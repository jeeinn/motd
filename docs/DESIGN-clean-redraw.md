# 方案：全屏干净重绘（破 ADR-027 白名单红线）

> 状态：**已实施（阶段 1-4 代码 + 阶段 5 文档，均为本地提交、未推送）**。三方评估一致、文档定稿（架构师 / 交互设计师 / 团长，2026-11-24）。
> 基线：`feat/v090-display-i18n` @ `9814717`（ADR-071 视口有界重绘已落地）。
> 用户诉求原话："为了体验可以破红线啊……每次重绘保持界面干净，不追加输出是最好的体验了。我建议请架构师可以考虑一下，还有前端交互设计师。至于数据传输带宽，我觉得比传统网页要节省很多吧。"

## 1. 先用大白话讲清：两种"重绘"差在哪

终端论坛的画面更新有两种做法，本文档的建议是换一种：

| | 局部重绘（现在：CUU+EL） | 整屏重绘（建议：H+2J） |
|---|---|---|
| 打比方 | 在写满的纸上，用橡皮把旧字**一行行擦掉再写** | 拿板擦把**整块黑板擦干净**，从左上角重写一遍 |
| 历史回看 | 纸上方的旧内容还在，能往回翻 | **也还在**——板擦只擦眼前这块，不擦之前翻过去的记录 |
| 主要毛病 | 新内容比旧内容短时，下方留一片空白带，光标被甩到空白区底部（用户截图的问题） | 每次都干净，没有空白带，光标位置固定 |
| 额外好处 | 带宽最省 | 不用记"上一屏写了几行"，所以窗口缩放后错位也一并解决 |

**结论**：当前方案像"涂改"——省字节但留痕；新方案像"擦黑板重写"——多擦一下但永远干净，而且两者都不丢历史。

## 2. 一个必须澄清的事实（推动本次方案转向的关键）

曾担心"整屏清屏会抹掉用户往回翻看历史帖子的能力"。**这个担心不成立**：

- `ESC[2J` 只清**当前可视屏**，不清回滚历史区（scrollback）；
- 真正清历史的是 `ESC[3J`，本方案**明确禁止**；
- 备用屏（`?1049h`）才会让动画内容通常不进历史——这是不用备用屏的理由之一。

因此"保护历史"不构成"普通页继续用局部重绘"的理由。交互设计师核对后已撤回该边界，三方一致转为：**普通导航页以整屏重绘为目标态**。

## 3. 为什么决定破红线（三条实证）

| 维度 | 实测 / 论证 | 结论 |
|---|---|---|
| 带宽 | 单帧实测 310–414 字节；新序列 `ESC[H`+`ESC[2J` 固定 7 字节（1.7%–2.3%）；省掉逐行补清后，版块列表净降约 34 字节（−8%），其余持平 | 带宽不是代价，是**小幅收益**；比传统网页首页省 2–4 个数量级的优势保持 |
| 窗口缩放 | 旧机制靠 `screenLines` 记录上一屏行数定位，而 window-change 层拿不到 pageController，缩放后记录陈旧（ADR-071 已登记的代价）；新机制每次从 (1,1) 重画、不依赖旧行数 | 天然规避，无需再补 SIGWINCH 钩子 |
| 视觉 | 整屏重画只写内容行数 n，不再补清到 `max(n+1, up)`，故无 up−n 空白带；末行内容后的 `\r\n` 把光标带到第 n+1 行行首（输入位），不额外多写 CRLF | 彻底消除空白带、光标落底、当前屏残影 |

## 4. 最终方案

### 4.1 主方案

- 新增两个**无参数**服务端常量：`ESC[H`（光标回左上角）、`ESC[2J`（清当前屏）。
- **不用备用屏**（`?1049h`）：断连/崩溃时若没发出退出序列，用户终端会卡在备用屏、看不到主屏和历史——这是 TUI 最常见事故；且 `?1049h` 是 xterm 私有扩展，非 VT100 标准。
- 整帧**一次 Write** 送达（清屏+内容不分包），避免中间空白帧闪烁。当前 `render()` 已是单次 `io.WriteString`，满足前提。
- **精确帧结构**：`ESC[H` + `ESC[2J` + `n` 行内容 + 光标落在输入位。规则：
  - `n < H`：n 行内容每行以 `\r\n` 结尾（共 n 个），光标自然到第 n+1 行行首（输入位），**不再额外写 CRLF**（多写会多滚一行）；
  - `n >= H`：**末行的 `\r\n` 不写**，否则在屏幕底行换行会触发滚屏、把第 1 行顶出可视区（重演 ADR-071 修掉的问题）。光标停在末行行尾即可。
  - 状态栏仍在内容之后、不物理钉底。
- **n > 可视高度 H 时**：2J 清屏后从顶行写 n 行，超出部分自然滚入 scrollback，可视区显示末尾 H 行、光标在其后。这与当前"长详情"表现一致（会滚屏但绝不错位）；长内容的分页是独立立项项（见第 6 节第 4 条）。

### 4.2 重绘函数的分工（避免与彩蛋冲突）

主方案要移除"逐行 `\r`+EL 补清"的逻辑，但彩蛋 `/matrix` 帧间恰恰需要这种"局部覆盖不闪"的能力。两者必须并存、职责分离：

| 函数 | 语义 | 使用方 |
|---|---|---|
| `RenderCleanFrame(text string, height int)`（新增） | `H + 2J + n 行`，整屏重绘；用 height 判断 `n >= H` 时末行是否省 CRLF | 普通导航页（列表/详情/搜索结果）、登录屏 `showStart` 整屏状态更新 |
| `RenderFrame(text, prevLines, width, height)`（保留） | `prevLines > 0`：CUU+EL 局部覆盖（含 ADR-071 的高度钳制）；`prevLines <= 0`：追加 | **当前无生产调用**：页面走 `RenderCleanFrame`、彩蛋逐行追加、编辑器走 `line_echo` 的行内 CUU/EL。保留为"局部覆盖"能力（含其单测），供未来需要原地更新单行/单块的场景；不删除是为了不丢掉 ADR-027/071 已验证的钳制逻辑。 |

`pageController.render()` 恒用 `RenderCleanFrame`。由此 **`screenLines int` 与 `invalidateScreen()` 一并删除**：
- 整屏重绘不依赖"上一屏行数"，`screenLines` 无存在意义；
- 也不再有"追加模式"，`invalidateScreen()` 这个"打断连续性"的标记同样失去语义（每次渲染都是全屏）。
- 命令输出/提示/编辑器回显的"追加"是**这些写入路径自身的输出方式**，不需要 pageController 维护状态；它们之后的一次页面渲染自然清屏回到页面。
- 彩蛋的屏幕独占用独立标记（如 `matrixActive bool`），与重绘模式解耦。

### 4.3 实施节奏：一步到位，不分两阶段

用户明确要求"**优先用户体验好**"。分阶段（先只做彩蛋、普通页后补）会让先发布的版本对用户毫无改善，与其诉求直接冲突。因此：

- **默认一步到位**：Phase 1 与 Phase 2 合并，普通导航页直接切换整屏重绘；
- 仅在实施中回归面失控（例如 archtest 守卫改造牵连过广）时，才降级为两阶段，且 ADR-072 必须写明"普通页整屏重绘是目标态、不是可选项"；
- `/clear` 命令**当前不存在**（已核实 `ssh_handler.go` 无此分支）。若需要，必须作为**新增功能**在本次一并实现（新增命令、文案、测试），不能当作"已有能力"引用；若不实现，则从方案中删除该提法。

### 4.4 场景覆盖规则

| 场景 | 破红线后 |
|---|---|
| 版块列表 / 帖子列表 / 帖子详情 / 搜索结果 | 整屏重绘（`RenderCleanFrame`）；`back()` 双渲染的第二次自动覆盖第一次，无残影 |
| 彩蛋 `/matrix` | 见第 5 节 |
| 命令输出 `/who` `/whoami` `/stats` | **保持追加**——这是刻意的体验取舍，不是遗漏：查询结果是"要读的内容"，若清屏会当场丢失，用户需回看；追加后旧结果留在 scrollback 可上翻 |
| 登录流程逐行反馈 / device code 轮询 | **保持追加**（多步反馈是日志语义；轮询状态行可选改为行内 EL 覆盖，另议） |
| 编辑器回显 | **保持行内 CUU+EL**，不改成整屏（逐字符重画整屏会闪、且破坏退格精度） |
| 错误提示 `fail()` / `writeFixed` | 错误进状态栏随下一次页面渲染显示；`writeFixed` 追加一行保留可追溯。均不纳入整屏重绘 |

**关于"命令输出后一按导航键就清屏"的体验说明**（如实告知）：用户执行 `/who` 后，输出追加在当前屏下方；用户再按 `j/k` 时整屏重绘回列表，`/who` 的输出会离开可视区、进入 scrollback，向上滚仍可看到。这是"干净重绘"与"保留历史"的折中：当前屏永远只显示当前页面，历史查询结果靠终端回滚查看。


## 5. 彩蛋 /matrix 的交互约束

- **进入**：`ESC[H` + `ESC[2J` 清出动画区；第 1 行写固定提示 `[Esc 返回] · 约 1.2s 自动结束`。
- **帧间**：逐行追加雨帘（`height-2` 帧——24 行终端为 22 帧，约 1.1s；留 1 行提示 + 1 行余量，避免最后一帧的换行把提示顶出可视区）。**清屏后的空屏上逐行追加不产生残影**，因此不需要维护 24 行 ring buffer 做局部覆盖——这是对原"每帧覆盖 24 行"方案的简化，视觉等价、实现更小、带宽更低（每帧一行而非整屏 24 行）。
- **退出**：`ESC[H` + `ESC[2J` 清屏，随后 `p.render()` 重绘原页面。
- **软恢复三条路径**：`Esc` / 自然结束 / 断连 ctx 取消，统一 `defer` 收口，避免漏路径留脏屏。
  实现要点：`runMatrix` 原本是纯输出循环、不读按键；需把 `Serve` 主循环的 `msgs <-chan input.KeyMsg` 传进来，在每帧 `select` 中监听 `KeyEsc`（channel 关闭即断连），`handle()` 增加该参数以透传。**另有一处必解缺口**：`KeyDecoder` 只在有人调用 `Poll()` 时、过 25ms 决策窗口后才产出 `KeyEsc`；动画期主循环阻塞在 `handle` 内无人 Poll，真实用户按 Esc 会一直滞留在 `pending`（提示写着可返回、实际按不动）。故须把 `dec.Poll` 也传入动画循环，每帧（50ms）补判一次，Esc 最迟约 75ms 生效。
- **退出后重绘原页面**：`matrix` 分支在 `runMatrix` 返回后调用 `pc.render(ctx, sess)`；因动画期间不改 `p.screen/p.notice/p.selection`，`RenderScreen` 纯函数自然复现原页面，无需状态快照。
- **与页面渲染的独占**：`runMatrix` 在 `handle()` 内同步执行，主循环此时阻塞、不会并发触发 `render()`，独占天然成立；若后续引入异步渲染（如 presence 广播），需加显式 `matrixActive` 标记拦截。

## 6. 边界与已知代价（如实登记，不夸大）

1. **历史残影仍在**：`2J` 只清当前屏，已滚入 scrollback 的旧详情顶部行仍可上翻看到。这是"保留回看能力"的有意取舍，不是 bug。
2. **不是缩放即时重画**：window-change 后若用户不按键，当前屏由终端自行重排，可能短暂错位；下一次 `render()` 才正确。要即时对齐需新增 transport→pageController 通知钩子（可选增强，不阻塞本方案）。
3. **编辑器回显态不受益**：`line_echo.go` 走行内 CUU/EL，不经过整屏重画；缩放时编辑器回显仍可能错位，`loginPresenter` 的宽高是 pty-req 时的静态值。登记为已知边界，不作为否决理由。
4. **长详情无分页是 P0，但独立立项**：分页是信息架构问题（要动查询/焦点/渲染三条链），不并入本次重绘重构。本期低成本止损：详情页 footer 加"长主题可向上滚动回看"管理预期。
5. 带宽唯一例外：`/matrix` 若每帧都 2J 全屏重画约 1.4 KB/s → 30–40 KB/s，绝对值仍远低于 1 Mbps；按第 5 节"帧间用局部覆盖"实现则不触发该增量。

## 7. ADR-072 变更清单（编码时落实）

- **安全边界**：白名单扩为 SGR/EL/CUU + **无参** H + **无参** 2J；**永禁** CUD(B)、DECSET(?1049h)、OSC、带参 CUP（`\x1b[r;cH`）、带参 EL/其他 ED（1J/3J）。新序列零参数，杜绝参数注入面。
- **ADR-027 原文不删改**：需标注"已修订（ADR-072）"的是 **结论 2/3/4/5/6** 五条——结论 2（白名单扩）、结论 3（解禁无参 H/2J、仍禁 CUD/DECSET/OSC/带参 CUP/带参 EL）、**结论 4（pageController 不再"记住上一屏行数"，改为 append/redraw 显式状态；RenderFrame 仍是唯一消费点但新增 RenderCleanFrame 为受限第二消费点）**、结论 5（invalidateScreen 语义扩展为 screenMode 切换）、结论 6（整屏重画后取消超宽降级）；结论 1（导航原地重绘）语义不变，无需标注。文尾加修订说明指针。
- **ADR-071 标注**：其视口钳制/帧末归位机制在目标态被整屏重画取代，历史保留；其中"引入 ED/CUP 会抹掉用户历史"的表述按第 2 节事实修正澄清。
- **新增不变量**：整帧一次 Write；参数来源约束；不用备用屏；append/redraw 显式切换；scrollback 保护；普通导航页整屏重绘是目标态（非可选项）。
- **ADR-071 既有测试的处置**（实施时必踩，先写清）：`TestRenderFrameClampsCUUToViewport`、`TestRenderFrameNoHeightFallsBack`、`TestBackClampsCUUToViewport`、`TestRenderFrameClearsShrunkScreen` 四项断言的是 CUU 钳制/补清行为。改整屏重绘后：前两项若保留 `RenderFrame` 局部覆盖分支则继续有效（供彩蛋用），保留即可；`TestBackClampsCUUToViewport` 需改为断言"back 帧以 `H+2J` 开头、且不含超过可视高度的 CUU"；`TestRenderFrameClearsShrunkScreen` 的补清语义在新路径下由 2J 天然满足，改为断言"缩屏时以 2J 开头、不再逐行补清"。不得直接删除这些测试而不换成等价断言。
- **守卫同步**：`safe/ansi.go` 增 `CursorHome()/ClearScreen()`；`archtest/safe_test.go` 的 allowedANSI 与负向注入表；`frame_test.go` 白名单断言；`cmd/server` 端到端负向注入（用户文本含 `\x1b[2J` 必须显示为可见图示）；`AGENTS.md §3`、`CONTRIBUTING.md`。
- **登录屏这条第二条渲染路径（易漏）**：`loginPresenter`（`login_view.go`）有自己的 `screenLines` 和 `renderLoginScreen`（`login_screen.go:59` 调 `RenderFrame`），必须一并改造：
  - `showStart` / `showSuccess` 这类**整屏状态更新**改用 `RenderCleanFrame`（与普通页一致，消除登录屏的残留/空行）；
  - `line()` / `external()` 的**逐行反馈**（device code、轮询状态）保持追加；
  - ADR-071 加的 `loginPresenter.height` 字段在改用 `RenderCleanFrame` 后不再需要，可移除（保留也无害，实施时按最小改动决定）。
- **代价量化（评估口径）**：生产 6 文件净增约 30–60 行，测试 4 文件约 ±100 行，文档 3 处；无新依赖、无 schema/env/键位变更；风险等级中，真实待解仅三项工程问题（清屏/写入分片闪烁、`/matrix` 退出路由、状态页 writeSystem 前置清屏适配器）。
