## 1. P2-M0：补齐 P1 欠账（强制前置）

### 1.1 欠账事实（本轮核实）

`PHASE1-PLAN.md §2.10` 与决策台账 #6 明确要求 P1 在 ADR 里固化节点三不变量，但：

| 承诺 | 实际 | 证据 |
| --- | --- | --- |
| ADR-030 固化 slug 规则 / 归档不物理删 / seed 不可变 | **未落地**——ADR-030 实际是「认证审计与限流的纯内存边界」，全文无 slug / archived / seed 相关 ADR | `DECISIONS.md:482`、`grep slug\|archived\|seed DECISIONS.md` 零命中 |
| 禁止物理删：`nodes` 有 `status='archived'` 归档位 | **表无 status 列** | `0001_init.sql:144-149`：nodes 仅 `id/slug/name/description` |
| seed 节点不可删不可改名 | 部分满足——`0002` 用 `INSERT OR IGNORE` + slug UNIQUE，重放不会覆盖改名，但**无代码层守卫** | `0002_seed_nodes.sql` |

### 1.2 M0 DoD

1. 新增 ADR-048「节点 slug 规则 / 归档不物理删 / seed 不变量」——补上 P1 欠账，编号接当前最大 ADR-047（不复用 030）。
2. 新增迁移 `0008_nodes_status.sql`：`ALTER TABLE nodes ADD COLUMN status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','archived'))`（若确认 `nodes.status` 确有必要；见 §1.3 拍板点）。
3. 隔离环境演练：`v7 → v8` 迁移 + 回滚、带数据 kill-9 + WAL 恢复（沿用 OPS §5 手法）。
4. archtest 守卫：任何删节点代码路径必须失败；列表查询必须带 `status='active'` 过滤。
5. 全量测试绿（基线 749 + 新增）。

### 1.3 需用户拍板

- **P1 欠账是否必须在 P2 开头补**：不补则节点管理缺归档语义，直接做 CRUD 会撞 FK（`threads.node_id REFERENCES nodes.id`，物理删有帖节点会失败）。建议补。
- **`nodes.status` 是否必要**：若节点管理只做「创建 + 改名 + 改描述」不做「删除/归档」，可不加 status 列、只写 ADR 不变量。范围差别见 §2.1。

## 2. P2-M1：节点（版块）创建与管理（L）

### 2.1 范围切面（待用户选）

| 方案 | 内容 | 体量 | 代价 |
| --- | --- | --- | --- |
| **A（推荐）** | 创建 + 改名 + 改描述 + 归档（软删），完整 CRUD | L | 需 0008 迁移 + 管理员权限模型 + 5 个命令 |
| **B（收窄）** | 仅创建 + 改名/描述，**不做归档/删除** | M | 无迁移、无归档语义，但节点一旦建错无法下线 |

### 2.2 既定约束（不可推翻）

- **权限**：`MOTD_ADMIN_FINGERPRINTS` 公钥指纹白名单，比对**已认证会话的指纹**——绝不用用户提交文本（PHASE1-PLAN §2.10 / §4.6）。本阶段**不引入管理员角色 / 不做 Web**（决策台账 #6 + 三方论证 ADR-049）。**用户 2026-11-20 拍板采纳**。
- **slug 规则**：形如 `/dev/`、`/etc/`，字符白名单 + 层级深度限制，在 ADR-048 固化；`ValidateSlug` 只在有 CRUD 调用者时才实现（不写孤儿函数）——**M1 就是那个调用者，本轮必须实现**。
- **归档不物理删**：`threads.node_id` 有 FK，有帖节点只 `status='archived'` 归档、列表过滤，与 threads/posts 软删一致（ADR-038 同构）。**用户拍板：归档只改 node.status、threads 不动，历史帖详情页仍显示版块名**（GetNodeBySlug 不过滤 archived 的设计因此更连贯）。
- **seed 规则（用户 2026-11-20 修订）**：5 个种子节点（`/dev/ai` 等）**可归档、不可改名**——它们是示例版块，允许下线但 slug/name 保持。0002 的 `INSERT OR IGNORE` 保证重放不覆盖；代码层守卫只拦 rename，不拦 archive。原"不可删不可改名"口径按用户新决定作废。
- **审计**：治理动作（节点 CRUD + M1b 隐藏他人内容）复用 P1 的 `auth_events` 有界异步审计通道，经 outbox enqueue-only、提交后投递；记「谁/何时/命令/目标/结果」。**用户拍板采纳**。
- **对外接口继续冻结**：只做终端命令，不做 HTTP 管理端点。

### 2.3 命令面（用户 2026-11-20 拍板：list/create/rename/archive）

```
/node list                  列出全部节点（含 active/archived 状态）
/node create <slug> <name>  创建（管理员）
/node rename <slug> <name>  改名（管理员，seed 拒绝）
/node archive <slug>        归档（管理员；seed 允许归档；threads 不动）
```

DoD：命令白名单 + 越权负向测试 + seed 改名拒绝但归档允许 + FK 归档测试 + archtest 守卫 + 审计事件断言。

## 4. 管理员角色与管理入口设计（三方论证结论）

> 用户诉求：节点完整 CRUD / 移动合并要规划管理角色与权限，"管理员必不可少，但权限不要太复杂"，问"内置简单 Web 页还是其他方式"。
> 论证参与：PM（产品判断）、架构师（技术方案）、运维（可运维性与安全面），三方独立出论证书后综合。

### 4.1 核心结论：没有真实冲突，沿用既定方案

**"要管理员"与决策 #6「不引管理员角色」不是二选一。** 项目从 P1 起就已定好答案（PHASE1-PLAN §2.10:149）：**公钥指纹白名单 + SSH 命令**——有完整治理能力，但不建 `users.role` 字段 / RBAC 体系。三方一致推荐这条路，我认可。用户要的"管理员"是**治理能力**，不是**角色数据模型**。

| 决议 | 结论 | 一致性 |
| --- | --- | --- |
| `users.role` / RBAC | **否决** | 三方一致 |
| 内置 Web 管理页 | **否决**（本阶段） | 三方一致 |
| 公钥指纹白名单 `MOTD_ADMIN_FINGERPRINTS` | **采纳** | 三方一致 |
| SSH 命令为主入口 | **采纳** | PM + 架构师；运维倾向 CLI，但承认 CLI 不宜做在线主路径 |
| CLI / motdctl | 仅 bootstrap / 灾后恢复 | 架构师否决其在线主路径资格（见 4.4） |

### 4.2 最小权限模型（采纳）

- **谁能管理**：仅白名单列出的 SSH 公钥指纹；默认空 = 当前行为（无人能管）。比对的是**已认证会话指纹**，绝不认用户提交文本——公开邮箱注册无法自我提权。
- **授权**：把管理员公钥指纹写进 `.env`（0600、不进仓库）。用对应私钥登录即自动有权，无"谁来设第一个 role"的鸡生蛋问题。
- **撤销**：从白名单移除指纹 → 治理命令立即被拒；普通用户身份与内容不受影响（权力与内容身份解耦）。
- **判定点**：命令分发层**一个谓词** `isOperator(session.Fingerprint)` 收口，所有治理命令共用，不新造第二套。
- **审计**：复用 P1 的 `auth_events` 有界异步通道，只记治理动作（谁 / 何时 / 命令 / 目标 / 结果）——公开注册 + 可治理他人内容，必须可追溯。**P0**。
- **明确不做**：role 字段、RBAC 矩阵、分节点 ACL、角色继承、自助提权、Web 角色界面。

### 4.3 为什么否决 Web 页（三方的理由归并）

1. **推翻决策 #3**：对外接口冻结从 P0 沿用至今，P1-M5 邮箱刚再次选择"终端命令、不做 HTTP auth 端点"。
2. **安全面**：HTTP 认证 + 会话 + CSRF + 静态资源 + TLS 是一整套新公网面；1000 在线 / 1 Mbps 未压测就新增，同时加攻击面与带宽面。
3. **带宽**：1 Mbps 连静态资源开销都没计入；治理操作本就极低频，Web 的增量价值与代价不成比例。
4. **契约**：0.x 接口不稳，Web 一旦上线即焊死对外契约。
5. **用户群**：目标是终端用户，管理员本就在 SSH 里，Web 零增量价值；且 Web 必然配套角色 UI，与"权限不要复杂"背离。

**重议触发条件（满足才重新评估）**：出现非技术管理员 / 需富文本审核或批量操作 / 已有 Web 客户端可摊薄认证成本 / 1000 在线压测通过且契约进入 1.0。当前一条都不成立。

### 4.4 为什么否决 CLI 做在线主路径（架构师技术理由）

- `motdctl` 被刻意设计为**离线工具**：直连 SQLite 会绕过单写队列（chan 256 + `_txlock=immediate`）、领域不变量与 outbox 守卫；`restore` 对运行中库拒绝操作。
- 若改用 socket 常量驻服务新增特权入口：Windows 可移植性差、身份退化为 OS root、丢失会话指纹的审计粒度。
- 结论：**CLI 仅做 bootstrap / 灾后恢复补充**，在线治理走 SSH 命令。

### 4.5 一个被忽略的紧迫缺口（PM 提出，我已核实成立）

公开邮箱注册自 v0.3.0 已开，垃圾帖/滥用帖有了真实入口；但当前 `/delete` 仅作者可用（`canModify` 单点判定 `userID>0 && ownerID==userID`），**没有任何命令能隐藏他人内容**。"维护论坛"眼下最紧迫的不是节点 CRUD，而是**内容治理**。

- 建议新增 **P2-M1b**：一条内容隐藏命令，与节点治理共用同一套白名单，边际成本极低。
- 扩展点已预留：`internal/application/forum/delete.go:36-39` 的 `canModify` 注释明确写着"全项目唯一的所有权判定"——将来引入版主只在这里加分支，不散落。

### 4.6 节点移动 / 合并：推 P3，不进 P2

- **事实裁决**：`0007_posts_fts` 只索引 `posts.body_md`，`node_id` 不在索引列——**节点合并不影响 FTS**（架构师对；运维的"合并后必须重建 FTS"是通用谨慎口径，本场景不适用）。
- **真正风险**：单写事务里 `UPDATE threads SET node_id=...` 的持锁时间——3s 写超时 + 单写连接，数据量大时会阻塞全站写；这才是容量假设里的风险点。
- **结论**：这是数据迁移不是 CRUD，牵扯 FK / 归档态 / seed 不变量，需快照 + dry-run + kill-9/WAL 演练级门槛。当前仅 5 个 seed 节点、无扩张痛点证据，**推 P3**。P2 建错节点只归档另建。

## 10. 作者身份与 @ 提及（用户提问的答复，不进 P2 排期）

### 10.1 当前"发帖人对应什么"

| 层 | 事实 |
| --- | --- |
| 存储 | `threads.user_id` / `posts.user_id` → `users.id`（整数主键，FK）；`users` 另有 `username`（3–20 字符、NOCASE UNIQUE）与 `display_name`（默认空） |
| 生成 | GitHub 登录取 login 派生、邮箱注册取 email 本地部分派生（`AllocateUsername` 冲突加数字）；邮箱注册的 `display_name = username` |
| 展示 | **终端只显示 `#<AuthorID>` 数字**（`view.go:288-290` 的 `metaFixed`），不显示用户名——这是 ADR 里"作者名投影（R11）留存价值未验证、触显示契约、0.x 不固化"的既有决策落地 |
| @ 提及 | **零实现**；原始设计稿 §P1 提过"@提及与未读"，但 P1 走 RICE 时 R11 被判"不做"，从未排期 |

### 10.2 @ 功能的设计建议（待评估，不是承诺）

**前置决策**：@ 提及必须先把作者名投影到终端（推翻 R11 的"不做"）——但这次有正当理由：R11 当初是"无证据"，@ 提及让作者标识从"锦上添花"变成"功能必需"。建议投影用 `username`（稳定、唯一、已 NOCASE），不用 `display_name`（可为空、无唯一约束）。

**实现分层**（沿用现有信任域与三层守卫）：

1. **存储**：新增 `mentions` 表（`id / post_id / mentioned_user_id / created_at / read_at`），或先做"仅通知不落库"的轻版。
2. **解析**：在 `application/forum` 加提及解析器——**只从已净化正文提取** `@username`，匹配 `users.username`（NOCASE）；禁正则里的用户提交片段，遵循 ADR-019。
3. **展示**：提及名在终端是**用户内容**，必须走 `safe.RenderUser` 净化链（不能像 `metaFixed` 那样拼本地数值）；@ 自己不通知。
4. **通知**：复用 `auth_events` 或新建轻量通知表；终端提示"你被 @ 了 N 次"走 `RenderSystem` 固定文案，不含用户名原文。
5. **限流**：防刷 @（每帖 @ 上限 + IP/用户维度），复用 M2 内存限流器。

**风险**：① 触显示契约，需按 ADR-014 三层守卫评估；② 用户名含中文/特殊字符时 `@` 边界解析复杂（建议先只支持 ASCII 用户名，或明确分隔符规则）；③ 1 Mbps 下通知不能每条推送，聚合为一行摘要。

**建议排期**：P3（作者名投影 + @ 提及一起做），不与 P2 混——P2 的治理能力优先。

## 11. P2-M3：回复数计数投影（2026-11-20 用户拍板加入）

### 11.1 背景与现状

- v0.3.3 已把回复数格式从 ` N回复` 改为紧凑 ` rN`（`view.go` 的 `metaTail`），但核实发现 **`RowMeta.Replies` 在生产路径从未被赋值**——历史上也从未真正显示过回复数。
- 用户先拍板"暂搁"（不混进 v0.3.3 作者名 patch），随后 2026-11-20 明确"回复数计数投影加入 P2，并按团队建议放入执行顺序"。
- **定为 P2-M3**（M2 编辑功能之后）：这是展示完整性修补，不阻塞任何治理能力；`rN` 格式已就位、不会变坏，优先级低于 M0/M1/M1b 的治理主线。实际落地为 ADR-052（原规划号 051 因 M1b 加入顺延）。

### 11.2 技术路径（待架构师在 M3 开工时定稿）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A 写时维护 | threads 加 `reply_count` 列 + 0009 迁移回填；发帖/软删回复同事务增减；读时直接取列 | 需迁移 + 写路径每处维护计数（含 `/delete`、将来 `/edit`、节点归档/合并），一致性面大 |
| B 读时聚合 | ListThreads 的 SQL 加子查询 `SELECT COUNT(*) FROM posts WHERE thread_id=t.id AND status='normal'`，填 `RowMeta.Replies` | 无迁移；但列表查询变重（1 Mbps / 分页 20 行），需确认索引 `idx_posts_thread` 覆盖、EXPLAIN 无全表扫 |

**倾向 B（读时聚合）**：零迁移、零写路径改动，与项目"写事务稀缺"的约束同向；但 M3 开工前必须用真实数据量 EXPLAIN 验证，`<100ms` 才采纳，否则退回 A 并加 archtest 守卫维护点。

### 11.3 DoD（M3 开工时细化）

1. 主题列表真实显示 `rN`（非手工 set 的测试值）——用 e2e 或仓储集成测试证明：
   - 发帖后 r0 → 回复后 r1 → 软删回复后回 r0；
   - 跨 3 条主题计数互不串（验证 WHERE thread_id 与 status 过滤）。
2. 显示口径：`rN` 只在 `ScreenThreads`、N>0 时显示，其余符号不动。
3. 性能：分页 20 行聚合查询 EXPLAIN 走 `idx_posts_thread`，无全表扫；1 Mbps 下响应体增量可忽略。
4. 全量测试绿，无回归；ADR-052 记录方案选择与性能证据。
