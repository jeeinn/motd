## 2. 逐项详情

### R-06 详情屏内容分页（**已发布 v0.9.1**）

- **落地**：v0.9.1 已发版（ADR-073）。方案见 [`docs/DESIGN-detail-pagination.md`](DESIGN-detail-pagination.md)。采用**整块装箱分页**——正文按物理行切、回复按整条装，`n`/`p` 统一表示"往下/往上读一页"（无新键位），每页 `终端高度 - 7 - 帖子标题行数` 行且回复不超过 20 条；回复后走末页 Tail 查询恢复 ADR-068 焦点锚定。核心证据：数据层 keyset 已就绪、渲染层已在显示"按 n"、键位层却对详情屏空转；回复后的焦点回填代码已自认"超 200 条回退首行"。
- **问题**：详情屏一次渲染整帖全部回复，上限 `MaxPostsPerThread = 200`（`internal/application/forum/validate.go:18`，注释原文即"P1 再做内容分页"）。超过 200 条回复时**新回复不可见**，用户会以为没发出去；且详情屏内 `n` / `p` 翻页键无效（只在列表页生效）。
- **影响面**：长主题（技术长贴、争议帖）的核心阅读与追更体验。**用户 2026-11-24 判定属功能性缺口（内容不可达），非体验优化，故定 P0。**
- **方案方向**：把列表页的 `n`/`p` 语义扩展到详情（不做自由滚动——终端无鼠标，键盘分页更可控）；每页都带 footer 与状态栏；跨页焦点按 `Row.ID` 回填（ADR-066/ADR-068）；查询改成 Limit/Offset 并强制走索引。
- **优先级定案**：设计稿原评 **P1**、`ADR-072` 代价段称"独立 **P0** 项"，两者本不一致；本次按 **P0** 统一（`ADR-072` 的 P0 口径为准，设计稿 P1 评级作废）。不与其他项搭车：它同时动查询/焦点/渲染三条链，回归面大于此前任一单点修复。
- **风险**：同时触碰查询、焦点、渲染三条链，回归面大于此前任何一个单点修复；需虚拟网格 + 真实 SSH 双验证。

### R-07 草稿持久化落库

- **现状**：草稿只在**会话内**保留（ADR-067），断连即丢。
- **目标**：`drafts` 表 + TTL 清理 + 写队列，支持断连/重登恢复。
- **前置**：另立 ADR 评估与 ADR-010（单写连接）的背压关系，不能把草稿写入塞进业务事务。
- **估工** M（一次迁移 + 写队列 + 恢复路径）。

### R-08 全量 UI 文案 i18n

- **现状**：i18n 只覆盖 10 个 hint key 与 notice 前缀（`internal/presentation/terminal/i18n/catalog.go`），默认 zh 逐字节不变（ADR-070）。
- **缺口**：状态栏、footer、命令回显、错误文案、`/help` 分组标题仍是硬编码中文。
- **风险**：文案量大且散落在渲染层与命令层；需先定"哪些文案进 catalog、哪些保持硬编码"的边界，否则会变成字符串搬家。

### R-09 resize 即时对齐（**已发布 v0.9.2**）

- **原问题**：终端缩放后若用户不按键，当前屏仍是旧宽度排版的字节、由终端自行重排，**下一次 `render()` 才对齐**（ADR-072 边界 2；ADR-071 代价 2 同源）。
- **落地（ADR-074）**：transport 在 `window-change` 且尺寸真变化时非阻塞投递一条通知（`Session.ResizeNotify()`，容量 1、永不关闭）；`inputHandler.Serve` 主循环收到后自行调 `pc.render(sess)` 按新宽高整屏重绘当前屏，不再等下一次按键。
- **分层约束**：transport 只投信号、**绝不直接 Write 终端**——页面状态归 handler goroutine，直接写会与按键回显字节交错并构成状态竞态；`pageSession` 接口零改动，依赖方向与 archtest 守卫不变。
- **不做什么**：不调 `pc.refresh()`（会把详情页踢回第 1 页并重查库）；命令输入 / 编辑器 / 登录 / 邮箱交互态跳过重绘（逐字节追加回显会被 `H+2J` 抹掉）。详情页 resize 只重绘当前已装箱的一页，不重算分页装箱，按 `n`/`p` 后即按新容量重排。
- **验证**：transport 通知语义 + 真实 SSH `window-change` 端到端；`resizeRedrawable` 6 项表驱动 + 真实 SSH 重绘闭环（含交互态跳过 / 恢复）。四门禁 + 两闭环全绿，测试函数 1114 → 1119。
- **状态**：v0.9.2 已发版（ADR-074，代码 `5a31ea4`）；生产升级需另行授权并按 OPS 建回退点。

### R-10 差异行增量渲染

- **现状**：每帧重发整屏字节（视觉上只有一屏），未做差异行优化。
- **背景**：ADR-027 曾按 FF09 延后，理由是"属浏览器端 Frame 增量同源能力，不提前引入"。
- **结论**：**不建议单独做**，与 R-04 的 Frame 增量协议一起设计——同一套 diff 语义服务两端，避免做两遍。

### R-04 浏览器端 TUI 帧传输（P5 主线）

**状态**：方向已定（用户 2026-11-21 拍板为 P5 主线），**未开工，开工前需新 ADR**。这是对既有冻结口径（`archived/P3-PLAN.md` §8 / `archived/PHASE1-PLAN.md` §1.2）的正式解禁。

**方案**：服务端渲染语义 Frame + 本地键盘渲染器，与终端共用 ViewModel、独立渲染；Frame 增量 ops（upsert/remove/move/overlay/focus）+ seq/base_seq 恢复；不采用 xterm.js，JS ≤15 KB gzip。

**现状（代码事实）**：`internal/transport/websocket/doc.go`、`internal/presentation/browser/doc.go` 各 3 行纯占位——从零建，非续写。

**风险 / 前置**：

- 重议触发条件（`archived/P2-PLAN.md`）为"1000 在线压测通过 + 契约进 1.0"，**当前一条不满足**；用户拍板属产品层强制解禁，需在开工前正面处理"无容量背书下开新公网入口"。
- 0.x 对外契约一旦上线即焊死；容量 1 Mbps / 1000 在线未验收（ADR-059、R-03）。
- 安全边界：浏览器端用 `textContent`，与终端 `RenderSystem`/`RenderUser` 同等严格；WebSocket 校验 `Origin`，不依赖 `SameSite=Lax`。
- 量级 L，多模块；新 ADR 从 **ADR-077** 顺延（解禁决策 + Frame 协议 + Origin 校验 + 双端安全边界）。
- 容量验收是否作为 P5 硬前置，需用户再拍板。

### R-03 容量与压测

- 当前最小压测集给的是回环环境相对延迟基线，**不构成 1 Mbps / 1000 在线验收证据**。
- 目标机器与真实网络下的 100/300/500/1000 分档实测仍未做；提升 MaxConns 后的行为未验证。
- 触发条件：有明确的目标机器规格与网络环境后再排期。
- 注：v0.9.0 的整屏重绘已把帧开销压到 **310–414 B/帧**（实测），比传统网页低 2~4 个数量级，但这是单帧量级事实，不等于并发容量结论。

### R-14 `/game` 游戏指令与排行榜（**V1.0 已随 v0.11.0 发布**）

- **状态**：用户 2026-11-25 拍板立项，决策见 **ADR-078**。专家团（产品 / 研发 / 运营）三轮方案评审完成，结论已收敛。**尚未写任何代码、未迁移、未提交**；进入实施前需按 AGENTS.md §5 另行确认。
- **目标**：给论坛用户无聊时的短时消遣，用"刷新个人最佳 + 看榜首易主"补现有彩蛋缺的回访钩子。定位为**回访钩子（Retention）**，不承担获客。
- **拍板结论（用户 4 项决策，均按推荐）**：① 立项 R-14 + ADR-078；② MVP 做 **2 款**游戏（2048 + Snake）；③ 每日计分上限 **10 局**；④ `/stats` 游戏榜段放 **V1.1**。
- **游戏选型**：V1.0 = **2048**（回合制，一键一帧，最省带宽）+ **Snake**（输入驱动渲染，非定时器刷屏）；扫雷 Minesweeper 为 V1.1。否决俄罗斯方块（实时帧 = `/matrix` 式流量风险）、猜数字（过浅）、对战类（需匹配与等待态）。V1.0 白名单 `{2048, snake}` 放应用层，DB 不加 CHECK 枚举，V1.1 加游戏为纯代码改动、无新 migration。
- **命令结构**：`/game`（无参 = list）、`/game list`、`/game play <name>`、`/game top [game]`（周榜）、`/game top all [game]`（总榜荣誉墙）。独立 `GroupGame` 展示分组（不并入彩蛋组），无需权限、访客可玩；`/help` 的 printed map 为通用遍历，新增分组零改动。
- **架构落点**：game mode 状态机（类比 `emailFlow`）——`pageController.game` 每会话一份，按键在 `handleOne` 的 editor 分支之后、`h.handle` 之前路由，主循环不阻塞；断线随 `Serve` 返回自然销毁（无额外 TTL），6h 绝对上限兜底；退出 `pc.game=nil` + `pc.render(sess)`。三层：`domain/game` 纯状态机 → `application/game` 用例与端口 → `infrastructure/sqlite/repo_game.go`；cmd 加 `case "game"`。棋盘/固定文案走 `RenderSystem` + `RenderCleanFrame`（H+2J 整屏重绘，禁纯追加否则 scrollback 随步增长）；用户名一律逐段 `RenderUser`；game name 零回显原始输入（错误分支不回显 `inv.Args`，成功仅回显白名单常量）。
- **数据与计分**：新增迁移 `0012_game_scores.sql`（须同步 `indexes_test.go` 的 want→`[1..12]`）。V1.0 两表：`game_scores`（含 `is_counted` 留痕列）与 `game_leaderboard_week`；`game_events` 埋点表与其 `session_start` 分母、**TelemetryBuffer** 均放 V1.1。周榜/总榜走**结算增量 UPSERT**（`game_end && counted` 时同 `WriteTx` 写 `game_score` + UPSERT 周表 `best_score=MAX`），无定时器、无缓存；rank 不落库、查询期派生；总榜从周表 `MAX` 聚合不建新表。
- **写库矩阵（P0 正确性）**：`is_valid=false` → 不写 `game_scores`；`is_valid=true && is_counted=false`（每日超限）→ **写 `game_scores` 但不 UPSERT 周表**；两者皆 true → 写 `game_scores` + UPSERT 周表。`CountToday` 数的是 `game_scores` 当日行数（**含超限局**），故超限局必须落库留痕——否则第 12 局会被误判"当日仅 10 局"而绕过上限刷榜。`is_valid` 判定在 domain 纯函数，`is_counted` 在 application 用例读 `CountToday<10`；三者（计数 + 写分 + UPSERT）同一 `WriteTx`，靠 ADR-010 单 worker 串行保证原子。
- **榜单与防刷**：最佳成绩制（当周单局最高分，不累加）；周榜与总榜**均只聚合 `is_counted=true`**，口径一致；有效局门槛（2048 有效移动≥5 且得分≥4 / Snake 食物≥1）为**观察期可校准参数**，按周监控 `is_valid=false` 占比（>30% 下调 / <5% 收紧，目标 5%–30%，不误伤新手优先）；第 11 局起话术为正向回访钩子「今日挑战次数已用完，明天再来刷新纪录」，仍可玩、显示分数、留埋点，只是两榜不计；只 `IsUser()` 上榜，分数由服务端状态机算出（`Submit` 无分数入参），访客不入库。
- **护栏**：输入驱动帧渲染 + 帧率节流（两次出帧≥100ms，≤10fps）+ 单局时长/步数上限；并发 ~16 仅作灾害闸门（撤销早期"并发 ≤2"——那是 `/matrix` 12fps/29KB/s 的需求，Snake 实为 400–600B/帧、约 2–3KB/s/会话，限 2 会误伤正常用户）。只用 ASCII + 基础 16 色 SGR，禁 256 色/真彩（§4 冻结）、禁备用屏/OSC/3J。
- **分期**：V1.0（M，约 5–7 人日）= 2 款游戏 + `game_scores` + `game_leaderboard_week` + `is_valid`/`is_counted` 分层 + 双榜查询；**不做** `game_events` 埋点表、`/stats` 游戏榜段、历史荣誉墙独立表。V1.1（数据驱动）= 扫雷、`game_events` 埋点与 `session_start` 分母、`/game score` 个人统计、`/stats` 游戏榜段（追加语义 + 用户名逐段 RenderUser，不整屏重绘）、有效局阈值调优。
- **风险（P0/P1）**：archtest 违规（P0，光标控制只在 presentation 消费点、ESC 零内联）；刷分（P0，服务端算分 + 同事务原子限流 + 超限局留痕）；scrollback 增长（P1，整屏重绘 + 底行不写 CRLF）；单写队列背压（P1，结束才写一次、队列满降级固定提示）。
- **遗留待 V1.1 前置解决**：`is_valid=false` 与超限局的 `game_end` 埋点必须写（否则阈值校准无数据源）；参与率分母需 `session_start` 事件（公钥重连不计 `login_success`，ADR-064，不可复用登录埋点）；「距上一名差 X 分」查询期相邻行派生、不在 Top N 显示「未上榜」。

### R-15 社区运营优化：置顶/取消置顶、回复投票、白名单热重载（**已发布 v0.10.0**）

- **状态**：用户 2026-11-25 拍板立项，范围收敛为**四项**——① 置顶主题 ② 取消置顶 ③ 回复投票 ④ 管理员白名单热重载。决策见 **ADR-079**。**已实施并随 v0.10.0 发布**：新增迁移 `0012_threads_mark`、游标升 v2（兼容 v1）、2 条管理员命令，真机 SSH 冒烟 6 项全通过；实施期发现并修复热重载 SIGHUP 反注册 P0（见 CHANGELOG v0.10.0）。⚠️ 迁移编号 0012 与 ADR-079 原规划的 0013 有偏差（R-14 未实施、0012 空闲，为保持连续性改用 0012）。
- **明确不做**（本轮已排除）：举报入口、用户封禁/解禁、内容审核流、作者转让/认领、编辑时间窗/版本历史、IP 封禁、隐藏内容列表/批量治理、role/RBAC、Web 管理端。前几项在 ADR-050/053 已明确否决或全库无授权，不重复评估；标题变色（TitleMark，用户 2026-11-21 拍板的长期方向）**不在本版**，本版只复用其前缀渲染位做公告/置顶。
- **① 置顶 / 取消置顶**：走"**普通主题标记**"路线，非独立命令发公告——管理员在已发布主题上执行 `/pin`（置顶）、`/unpin`（取消置顶），写 `threads.mark` 标记字段（新迁移 0013，不改历史迁移），置顶主题在列表前置并带 `[置顶]` 前缀。前缀样式复用 `StyleNotice`（琥珀 `[33m`，`P4-PLAN.md:61` 已留位）；`Safe` 白名单不变。**keyset 游标须升版**：现有格式 `v1|<sort>|<last_reply_at>|<score>|<id>`（`cursor.go:11`）无置顶维度，置顶排序会破坏分页连续性，须升 `v2` 纳入 mark 维度并兼容 v1 解码（旧游标不失效）。仅管理员可用（`requireAdmin` 单点，ADR-049）；写审计复用 `EventAdminAction`（`adminActionEvent`）。置顶不参与 karma、不加权（沿用 ADR-014 语义）。
- **② 回复投票**：**底层已就绪、只差命令面接线**——`domain/vote` 已定义 `TargetPost`（`vote.go:11-13`，`Valid()` 放行）、`application/forum/vote.go:57-140` 的 `applyVote` 已支持 post 目标解析（`tx.PostThreadID`）、karma 作者（`tx.PostOwner`）、事件 PostID 回填，仓储与集成测试均已覆盖。缺口仅在 `cmd/server/page_controller_m3.go:49` 硬编码 `vote.TargetThread`。本版做法：扩展 `/vote` 在详情页按回复 ID 定位目标（或新增 `/vote post <id> <up|down|rm>`，命令面口径开工时定），复用现有 Service/仓储零改动；与主题投票共用**同一票型与限流**，不新造第二套。
- **③ 管理员白名单热重载**：消除"改 `MOTD_ADMIN_FINGERPRINTS` 必须重启"痛点。现解析在启动期 `config.ParseAdminFingerprints`（`config.go:128-133`），白名单复制进 `forum.Service`（`WithAdminWhitelist`）。本版做 SIGHUP 触发的**原子替换**：配置层重新解析（非法指纹拒绝替换、保留旧白名单并告警，不 half-apply），经线程安全容器原子换入 `Service`，`CanAdmin` 判定谓词与 requireAdmin 单点**完全不变**（ADR-049 不推翻）。此方向曾在 `P2-PLAN.md:251` 推 P3、`OPS.md:225-229` 标"不做"，本版**明确推翻该搁置**，理由：分钟级重启窗口在真实治理中不可接受。
- **技术底线（开工不可省）**：置顶/取消置顶与治理动作一样走 `requireAdmin` → `CanAdmin` 单点（archtest `node_admin_test.go`/`moderation_test.go` 守卫，绕过直接判失败）；游标升版必须双向兼容 v1（存量用户翻页不失效）；热重载失败关闭（非法配置保留旧值）；回复投票不绕过发帖写限流与 self-vote 禁令（ADR-057）；渲染前缀走 `RenderSystem`、作者名走 `RenderUser`（ADR-019/026）。
- **开放项（开工时定，不阻塞立项）**：`pin` 与 `announce` 是否分两级标记（建议分：置顶=排序提前，公告=额外 `[公告]` 前缀）；置顶是否限每版块 1 条；热重载的触发方式（SIGHUP vs 配置文件 watcher，建议 SIGHUP——与 systemd 既有运维路径一致）。
- **估工**：M（约 4–6 人日：置顶含迁移与游标升版 M，回复投票 S，热重载 S）。
- **风险（P0/P1）**：游标升版破坏存量翻页（P0，双向兼容测试 + 真实 SSH 分页回归）；置顶排序与 `SortScore`/`ListThreads` 的 keyset 语义冲突（P0，需明确置顶是"独立前缀层"而非新 sort 值）；白名单热重载 half-apply 造成权限真空或越权（P0，原子替换 + 非法拒绝 + 审计）；回复投票的自投票/重复投票绕过（P1，复用 Service 既有校验）。
